# ADR 0002: API-owned sessions

- Status: accepted
- Date: 2026-10-02

## Context

The API needs to know who is calling before it sets a tenant context
([ADR 0003](0003-tenancy.md)). One process serves the API, the project is small,
and the machine it runs on is shared. Identity must not be split across two
services, and nothing about a login may reveal which accounts exist.

## Decision

The API owns authentication. There is no external identity provider.

**Passwords.** argon2id through `argon2-cffi`, with the OWASP minimum
parameters (19 MiB, 2 passes, 1 lane). Hashing runs in worker threads behind a
semaphore of two, so a burst of logins cannot exhaust memory. Hashes live in a
`credentials` table, apart from `users`, with forced row-level security, no
policy and no app grant.

**Sessions.** A login creates a 256-bit random token, sent once in a cookie. The
database stores only its SHA-256, so a database read cannot be replayed as a
session. The cookie is `HttpOnly; SameSite=Lax; Path=/`, and `Secure` outside
the demo and test environments. A session ends at the first of: 12 hours
without use (idle), 7 days after login (absolute), or logout, which revokes it
server-side. Expired, revoked and unknown sessions are indistinguishable (401).

**Reaching sessions before there is a tenant.** Login and session lookup happen
before any org context exists, and forced row-level security binds even the
table owner, so a `SECURITY DEFINER` function owned by `inspection_owner` would
see no rows. The functions in schema `auth` are instead owned by
`inspection_auth`:

- `NOLOGIN` and `BYPASSRLS`; it owns nothing but those four functions and holds
  only the table grants they need.
- Each function pins `search_path`, has `EXECUTE` revoked from PUBLIC, and is
  granted to `inspection_app` alone.
- The app role passes a token hash and gets back a session and user id, or
  nothing. It never reads a session row.
- Lifetimes are clamped inside the functions (7 days absolute, 12 hours idle),
  so a bug cannot create a longer session. `last_seen_at` moves at most once a
  minute, so a busy session is not a write per request.
- `inspection_owner` may `SET ROLE` to the auth role but does not inherit its
  privileges. Migrations use that to create the functions as the auth role, and
  the seed uses it once to write demo credentials. This does not widen the
  owner's reach in practice: the owner owns every table and could already turn
  row security off. The catalog tests pin the membership exactly.

**Timing.** An unknown email costs the same as a wrong password: login runs a
full argon2 verification against a throwaway hash and returns the same status
and body.

**Authorisation.** Every org-scoped route takes the org from the path, then
checks membership under a user-only context before any org context is set. A
non-member gets 404, the same answer as for an org that does not exist. Roles
(`owner`, `admin`, `inspector`, `viewer`) are checked in the API after that, so
only members ever see a 403. Row-level security remains the wall behind it.

**Cross-site requests.** `SameSite=Lax`, an Origin check on every unsafe method
(a missing or foreign Origin is a 403), and JSON-only bodies. Responses carry
`nosniff`, `no-referrer` and `no-store`.

**Rate limiting.** Login attempts are counted per client IP (100) and per email
(5) in a 15-minute sliding window, in memory. An attempt is counted before it is
verified, so concurrent guesses cannot all pass the check. Unknown emails count
too, so a lockout never confirms an account. A successful login clears the email
counter. Logins waiting for a hashing slot beyond 20 get a 503, so a flood
cannot queue unbounded work.

**Signup and invites.** None exist. When one is added it must return one generic
answer whether or not the email is taken: the unique constraint on
`users.email` ignores row-level security, so any "already registered" response
would reveal accounts in other orgs. The route-walker test fails if a route with
`signup`, `register` or `invite` in its path appears, until a test for that
generic answer exists.

## Alternatives considered

- **Auth.js.** Would split identity between the web app and the API.
- **Keycloak or Zitadel.** Hundreds of megabytes of JVM or Go on a machine with a
  few gigabytes free, for a feature set this project does not need yet. An
  OIDC/SSO path can still be added at the API later.
- **A sessions policy scoped to the auth role** instead of `BYPASSRLS`. It would
  also work; a role that bypasses nothing it does not own was judged no safer
  and harder to review than one that owns only four functions.

## Consequences

- **The login limiter is per process.** With more than one API process each
  counts separately; move the counters to a shared store before scaling out.
- **A per-email limit can lock a known address out** for the window. The window
  is short and the alternative (no per-email limit) leaves online guessing open.
- **Client IP.** The limiter uses the connection's address, except for a request
  that comes from a proxy listed in `TRUSTED_PROXIES` (in Compose, the web
  service, which appends the address of the socket each request arrived on, because
  Next.js's rewrite alone passes the header through as the client wrote it). For those the
  rightmost `X-Forwarded-For` entry that is not itself a trusted proxy is used:
  each proxy appends on the right, so the left side is whatever the client
  claimed. A request from anywhere else, such as one sent straight to the API's
  port, keeps its socket address and its header is ignored, so a forged header
  cannot dodge or aim the limit. Names resolve to addresses and are re-resolved
  every 30 seconds; a name that does not resolve trusts nothing. Nothing is
  trusted when the setting is empty. Behind a further reverse proxy the web
  service sees that proxy's address, so list its address in the API's `TRUSTED_PROXIES`
  before relying on the per-IP limit; until then the limit is one
  bucket per proxy (hence 100, not a tight number) and the per-email limit is the
  real brake.
- **The app role is trusted for authentication.** `auth.verify_login` returns a
  password hash and `auth.create_session` accepts any user id, because password
  verification happens in the API. Code execution in the API is therefore
  account takeover, and hashes could be cracked offline. The functions limit the
  app role to these operations; they do not make it harmless.
- **Not built:** password change or reset, MFA, session listing or revocation of
  other sessions, deleting expired session rows, and the admin surface for
  security events. Failed logins are logged without the email; they are not yet
  in `audit_events`, which is org-scoped.
- **The demo password is public.** It is published in the README and exists
  only on seeded synthetic data; the seed refuses to run unless
  `APP_ENV=demo`.
