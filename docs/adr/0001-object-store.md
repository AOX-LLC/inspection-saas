# ADR 0001: Garage as the object store

- Status: accepted
- Date: 2026-10-02

## Context

Site photos, tiles and reports are binary objects that do not belong in
Postgres. The store has to be private by default, speak the S3 API (so clients
and presigned URLs are standard), run in a few tens of megabytes of memory on a
shared machine, and be replaceable without touching callers.

The API must never proxy object bytes. Clients upload and download directly
with short-lived signed URLs; the API only decides who may.

## Decision

Run **Garage v2.4.1**, pinned by image digest, as the `objectstore` service.
All S3 access goes through `api/app/storage/`, so changing the store means
changing configuration, not call sites.

- **Access.** Private by default: nothing is readable without a signature. One
  access key, generated by the `secrets` service and imported by Garage, is
  allowed read and write on one bucket (`inspection-uploads`). The key may not
  reconfigure the bucket.
- **Ports.** The S3 API is published on `127.0.0.1:4703`. Garage's RPC and admin
  ports are not published. 4704 is reserved and unused: Garage has no console.
- **Addressing.** Path-style, region `garage`. boto3 is configured with
  `request_checksum_calculation="when_required"`, because recent boto3 versions
  add checksums that non-AWS stores do not all accept.
- **First boot.** A fresh Garage has no layout, bucket or key. The one-shot
  `objectstore-init` service runs `python -m app.storage.init`, which calls the
  admin API to assign the layout, import the key and create the bucket, then
  sets CORS through the S3 API. Setting CORS needs bucket-owner rights, so the
  key holds them for that one call and loses them again. Every step can be
  repeated. The image is built from scratch with no shell, which is why the
  init is Python and why the health check is the binary's own `status` call.
- **Process.** Garage runs as a non-root user with a read-only root filesystem
  and every capability dropped. It mounts only its own secrets, not the whole
  credentials volume.
- **Keys.** Object keys are built only on the server, from database UUIDs:
  `orgs/{org_id}/projects/{project_id}/files/{file_id}/original`. The builder
  accepts `UUID` objects and nothing else, so no client string can reach a key.
  The `files` table has a check constraint binding the key to the row's own
  org, project and id.
- **Uploads and downloads.** See [ADR 0002](0002-auth.md) for who is allowed;
  [architecture](../architecture.md) describes the flow. In short: a presigned
  POST pins the key, one content type and a size, the API checks the stored
  bytes when the upload completes, and a presigned GET fixes the response
  content type and `Content-Disposition`.

## Alternatives considered

| Store | Licence | Why not |
| --- | --- | --- |
| SeaweedFS | Apache-2.0 | Most features (policies, IAM), but heavier with a larger surface. The fallback if Garage's licence is ever a problem; swapping it changes only configuration. |
| RustFS | Apache-2.0 | Reached 1.0 in September 2026, two weeks before this decision, and had a critical hard-coded-credential vulnerability (CVE-2025-68926) fixed in December 2025. Too young. |
| MinIO Community Edition | AGPL-3.0 | No longer distributed as images since October 2025; the repository is archived and source-only. |

## Consequences

- **Licence.** Garage is AGPL-3.0. This repository only references the
  unmodified official image as a separate service; no Garage code is linked or
  vendored. The licence's network clause applies to someone who modifies Garage
  and offers it to users, which this project does not do.
- **No bucket policies, no versioning.** Neither is needed. Authorisation is by
  signature and by key, and the API decides who may obtain a signature.
- **Presigned URLs are bearer tokens.** Anyone holding one can use it until it
  expires (5 minutes by default, never more than 15). They are never logged and
  are not written to the audit trail.
- **A POST policy cannot check file content.** The store enforces the declared
  type, key and size; the API inspects the leading bytes when the client calls
  `complete`. An upload could in principle be replaced by a second POST inside
  the same 5-minute window, after `complete`. Downloads force the content type
  stored in the database, so the replacement cannot change how the file is
  served, but the bytes could differ from what was checked. Closing this needs
  a server-side copy on completion; it is not built.
- **Rejected and abandoned uploads.** Rejected objects are deleted, but the same
  POST can still be replayed inside its window. A `pending` row that is never
  completed stays until a cleanup job exists; an org may hold at most 100 at once.
  There is no per-user quota or storage limit: Garage's capacity setting is a
  placement weight, not a quota.
- **Not verified here:** behaviour behind a public hostname or TLS terminator
  (signatures bind to the host, so `S3_PUBLIC_ENDPOINT` must match what the
  browser uses), and behaviour under concurrent load.
